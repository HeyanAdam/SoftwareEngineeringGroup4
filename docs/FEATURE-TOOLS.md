### 1.3 AI 文字答疑（⭐ 全系统技术核心）

| 项 | 内容 |
| --- | --- |
| **需求** | 3.5：自然语言提问、**引导式分步解题（不直接给答案）**、多轮深度追问、答疑记录留存 |
| **现状** | 🟡 会话与消息的增删查已通，回答是**关键词规则**（假 AI），需替换为真实大模型 |

| 工具 | 用途 | 状态 |
| --- | --- | --- |
| 前端对话界面（气泡、输入框、Enter 发送） | 交互 | ✅ |
| **SSE 客户端**：⚠️ **不能用原生 `EventSource`**（它无法携带 `Authorization` 头，而本项目 token 存在 localStorage、后端用 `HTTPBearer` 校验）。**必须用 `fetch` + `ReadableStream` 读取流式响应** | 接收**流式输出**，做打字机效果（需求 5.1 要求 ≤5 秒响应） | ⬜ |
| （备选）改用 **HttpOnly Cookie** 鉴权后，才可以使用原生 `EventSource` | 实现更简单，但需改造后端鉴权与 CORS 凭据配置 | ⬜ 备选 |
| FastAPI `StreamingResponse`（或 WebSocket） | 把大模型的流式结果转发给前端 | ⬜ |
| **🔵 大模型 API**（DeepSeek / 通义千问 / 智谱） | 生成解答 | ⬜ **需申请 Key** |
| **提示词工程** | 约束"分步讲解、不给最终答案、语气口语化" | ⬜ |
| MySQL `chat_sessions` / `chat_messages` | 会话与消息留存 | ✅ |
| Redis | **缓存相同问题的答案**（省钱）、限制单用户每日提问次数 | ⬜ |

**实现难点与坑**

| 坑 | 说明与对策 |
| --- | --- |
| 不流式输出体验差 | 大模型生成一段完整回答要 3-10 秒，必须流式；否则用户以为卡死 |
| 上下文太长导致费用高 | 只带最近 6-10 轮对话 + 相关知识点片段（`chat_service.py` 里已有 `MAX_HISTORY_FOR_CONTEXT` 的雏形） |
| 直接给答案违背需求 | 提示词里必须明确"引导式"，并在验收时专门测这一点 |
| 费用失控 | 加 Redis 缓存 + 每日次数上限（如 50 次/人/天） |
| API Key 泄露 | **绝不能写进代码或提交到仓库**，放 `.env`（已在 `.gitignore`） |

**落地位置**：替换 `kaoyan-backend/app/services/chat_service.py` 里的 `generate_answer()` 函数。

**合规要求**（务必执行）

| 要求 | 做法 |
| --- | --- |
| ⚠️ **`robots.txt` 只是抓取约束，不是授权依据** | 它表达站点是否希望被爬，**不等于版权许可**；允许抓取 ≠ 允许二次分发 |
| **建立来源白名单** | 只从预先审核过的站点抓取（政府/考试院官网、开放许可站点），白名单入代码配置，新增需评审 |
| **许可证与服务条款审核** | 每个来源记录许可证类型（CC BY-SA / 政府公开信息 / 保留所有权利）与 ToS 是否禁止自动抓取或再分发 |
| **个人信息筛查** | 抓取内容含姓名、电话、身份证号等必须过滤或脱敏后再入库（个保法要求） |
| 控制频率 | 每域名 ≥1 秒/次，避免被判定为攻击 |
| **逐条记录来源与许可** | 每条存 `source_url` + `crawled_at` + `license` + `permission_note`（许可信息不能只在来源清单里写一次） |
| 不用付费/受版权资料 | 只抓官方公开信息 |
| **停止抓取与删除流程** | 收到通知后：移出白名单 → 停止抓取 → **删除库中相关数据与 MinIO 快照** → 记录处理范围与时间 |
| 建立 `docs/DATA-SOURCES.md` | 登记来源、许可证、审核依据与时间、删除记录，答辩时可说明合规性 |

| # | 项目 | 用途 | 办理要点 | 状态 |
