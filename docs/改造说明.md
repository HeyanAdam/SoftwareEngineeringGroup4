# 考研 AI 导学平台 · 鉴权与授权改造说明

> 本文只写「改了什么、为什么这么改、怎么用」。所有改动都以你上传的项目文件为基础：
> `app/core/*`、`app/models/user.py`、`app/modules/user/*`、`src/router/*`、`src/stores/auth.ts`、
> `src/utils/request.ts`、`src/layouts/DefaultLayout.vue` 的原有结构、命名、异常约定、接口契约一律保留，
> 没有另起一套体系。凡是与原项目或《权限表》有出入的地方，本文第 3 节单独列出。

---

## 0. 一句话结论

- **鉴权**：AuthX 1.7.1（MIT，免费商用）负责 JWT 签发、校验、吊销；密码仍用项目原有的 argon2-cffi。
- **授权**：严格按《权限表》5 张表 + ER 图重建，落地禅道 L3（角色 CRUD / 多角色分配 / 权限勾选 / 管理员全权限 / 审计日志）。
- **登录**：`用户名+密码` 与 `邮箱验证码` 两条通道都实现，验证码邮件走 QQ SMTP SSL 465，未配置时控制台回显兜底。
- **数据库**：MySQL 8（docker，端口 3307），建表脚本由 ORM 直接导出，不手写 SQL。

## 5. 鉴权链路（AuthX）

### 5.1 令牌怎么签、怎么验

`app/core/security.py`：

```python
auth = AuthX(config=AuthXConfig(
    JWT_SECRET_KEY=settings.SECRET_KEY,
    JWT_ALGORITHM=settings.JWT_ALGORITHM,
    JWT_ACCESS_TOKEN_EXPIRES=timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES),
    JWT_TOKEN_LOCATION=["headers"],
    JWT_HEADER_TYPE="Bearer",
))
```

`app/core/deps.py` 里的取当前用户，按 AuthX 1.7.1 的真实行为写成：

```python
rt: Annotated[RequestToken, auth.ACCESS_TOKEN]   # 注入的是 RequestToken, 不是 TokenPayload
payload = auth.verify_token(rt)                   # 这一步才拿到 sub / jti / exp
```

这里踩过三个坑，都已在代码里规避，你二次开发时别踩回去：

1. `Annotated[TokenPayload, auth.ACCESS_TOKEN]` 注入的实际是 `RequestToken`，直接取 `.sub` 会 AttributeError；
2. `auth.ACCESS_TOKEN` 是 property 返回 `Depends(...)`，不是可调用对象，不能 `inspect.signature`；
3. `auth.get_token_from_request` / `auth.is_token_in_blocklist` 在 1.7.1 里是 **async**，本项目用同步 DB 会话，所以 Authorization 头由 `read_bearer_token()` 手动解析（只认 `Bearer`，大小写不敏感），令牌合法性仍交给 `auth.verify_token`。

只有挂 `dependencies=[Depends(auth.access_token_required)]` 才会在缺令牌时 401；只写 `Depends(auth.ACCESS_TOKEN)` 会放行匿名请求。

### 5.2 令牌能被吊销（原项目最大的洞）

原项目 JWT 一旦签发就 24 小时内无法作废。现在两条独立机制：

- **吊销名单**：`auth.set_token_blocklist(_is_revoked)`，退出登录时把当前令牌写入（Redis 存 `sha256(令牌)`，不存原文，key 的 TTL 等于令牌剩余寿命）；
- **密码版本 `pv`**：改密 / 重置密码时 `auth:pwdver:{user_id}` +1，令牌 payload 里带签发时的 `pv`，对不上即失效。这条保证「改完密码，旧令牌立刻失效」，不依赖用户点过退出登录。

### 5.3 登录安全性（对齐《明文密文说明》）

- 密码 argon2 慢哈希；登录失败统一回「账号或密码错误」，账号不存在时也跑一次哑哈希（等代价，防枚举）；
- 连续失败 `LOGIN_FAIL_LIMIT=5` 次锁 `LOGIN_LOCK_SECONDS=600` 秒，第 5 次直接回锁定提示；锁定期间即使密码正确也拒绝；
- 验证码 6 位数字、`EMAIL_CODE_TTL_SECONDS=300` 秒有效、一次性消费、错 5 次作废；
- 发送冷却 60 秒，且冷却键按 `{用途}:{邮箱}` 维度区分——否则「发过登录码后立刻发重置码」会被误拦（这是测试跑出来的 bug，已修）；
- 400/401 的响应体沿用项目原约定 `{code, message, data}`，40100 表示未认证。

### 5.4 `SECRET_KEY`

`.env.example` 里已经换成随机值（`secrets.token_urlsafe(48)` 生成）。同时 `config.assert_secret_key_safe()` 在应用启动时检查：**如果还是仓库示例值 `dev-only-change-me-please-...`，生产环境直接拒绝启动**，开发环境只打警告。这样即使有人把 `.env` 忘在默认值，也不会带着可伪造的 token 上线。

## 6. 授权链路

### 6.1 服务端（唯一的安全边界）

```python
@router.get("/admin/roles", dependencies=[Depends(require_permission("role:manage"))])
```

`app/core/rbac.py` 的判定顺序：`account_status == 1` → 角色里含管理员角色（`ADMIN_ROLE_ID=2`）直接放行 → 否则看 `sys_user_role → sys_role_permission → sys_permission.perm_key` 是否命中。

权限结果缓存在 `rbac:perm:{user_id}`，靠全局版本号 `rbac:perm:version` 失效：任何角色/权限变更只 `incr` 版本号，旧缓存整体作废，不用逐条删。

Redis 不可用时 `app/core/store.py` 自动降级为进程内字典，并在日志里明确警告「多 worker 部署请修 Redis」——降级是为了不让登录功能挂掉，不是让你在生产这么跑。

### 6.2 前端（只做界面显隐，不是安全边界）

- `src/stores/auth.ts` 新增 `permissions / roles / isAdmin / hasPerm()`；
- `src/config/menu.ts` 每个菜单声明所需 `perm`，`DefaultLayout.vue` 按 `hasPerm` 过滤后渲染，后台菜单单独分组；
- `src/router/index.ts` 守卫在有 token 的基础上增加 `meta.perm` 校验，无权限时提示并回首页；
- 403 只有「账号被禁用」才清登录态，其余 403（没这个权限）只提示不清 token——原项目 401/403 一律踢人的做法会让「点了没权限的按钮」直接掉线。

### 7.2 旧 `users` 表怎么办

你库里的 `users` 表是 **0 行**，所以这次迁移零风险。如果以后别的环境有数据，按下面搬（字段一一对应）：

```sql
-- sys_user.email 是 NOT NULL + UNIQUE, 旧库的 email 可能为空或重复, 这里先兜住:
--   空邮箱 -> u{id}@pending.local 占位(登录不受影响, 后台可改)
--   重复邮箱 -> 保留第一条, 其余加 dup{id}+ 前缀, 不让整个 INSERT 失败
INSERT INTO sys_user (user_id, login_name, email, password, account_status, create_time)
SELECT
    id,
    username,
    CASE
        WHEN email IS NULL OR email = '' THEN CONCAT('u', id, '@pending.local')
        WHEN ROW_NUMBER() OVER (PARTITION BY LOWER(email) ORDER BY id) > 1
             THEN CONCAT('dup', id, '+', email)
        ELSE email
    END,
    password_hash,
    IF(is_active, 1, 0),
    created_at
FROM users;

INSERT INTO user_account (user_id, user_name, major, target_area, create_time)
SELECT u.id, COALESCE(u.nickname, u.username), u.target_major, NULL, u.created_at
FROM users u;

-- 旧 users.target_school 是院校名称, ER 图只有编号列 target_school_id(院校主表属择校模块), 暂不迁

-- 原 users.exam_year(考试年份) 在 ER 图里没有对应列, 按权限表口径丢弃; 你的库该表为 0 行, 无实际影响

INSERT INTO sys_user_role (user_id, role_id) SELECT id, 1 FROM users;  -- 1 = 考研学生
```

搬完后 `sys_user_role` 里每个老用户默认挂「考研学生」；要提管理员，去后台「用户管理 → 分配角色」勾「系统管理员」。

## 8. 邮箱验证码邮件（方案 A+E）

1. 登录 QQ 邮箱 → 设置 → 账户 → 开启「POP3/SMTP 服务」→ 生成**授权码**（16 位，不是 QQ 密码）；
2. `.env` 里填：

```ini
MAIL_ENABLED=true
MAIL_HOST=smtp.qq.com
MAIL_PORT=465
MAIL_USE_SSL=true
MAIL_USERNAME=你的QQ邮箱@qq.com
MAIL_PASSWORD=授权码
```

3. 重启后端，`POST /api/user/email-code` 应返回 `{"channel":"smtp"}`；
4. **兜底（方案 E）**：`MAIL_ENABLED=false` 或发信失败时，验证码打到后端日志并在接口响应里返回 `dev_code`，前端直接回显。该行为由 `settings.mail_fallback_allowed` 控制，`APP_ENV=production` 时强制关闭（生产环境把验证码返回给前端 = 邮箱登录形同虚设），此时未配置 SMTP 会返回 503。

## 9.1 业务模块接入约定（只给契约，不实现业务）

改造范围只有鉴权与授权，因此**没有实现任何业务接口**（`/api/ai-chat`、`/api/plans`、`/api/files` 这些都在你自己的项目里，本次一行没动，`main.py` 里依然 include 它们）。鉴权层只提供三个符号，业务模块按需引用即可，不需要任何占位实现：

| `DbSession` | `app/core/deps.py` | 数据库会话依赖 |

| `require_permission("模块:操作")` | `app/core/rbac.py` | 生成权限依赖，缺权限抛 403，超管直接放行 |

接入写法（业务模块自己加，改造包不代写）：

```python
from typing import Annotated
from fastapi import Depends
from app.core.deps import CurrentUser, DbSession
from app.core.rbac import require_permission
from app.models.user import User

# 只要求登录
@router.get("/plans")
def list_plans(user: CurrentUser, db: DbSession): ...

# 要求某个权限点
StudyPlanEditor = Annotated[User, Depends(require_permission("studyplan:add"))]

@router.post("/plans")
def create_plan(user: StudyPlanEditor, db: DbSession): ...
```

测试期间修掉的 5 个真实问题（都是跑出来才发现的，记在这里防止回归）：

1. SQLite 下 `BigInteger` 主键不自增 → `models/types.py` 用 `with_variant(Integer, "sqlite")`；

4. 删角色 / 改用户角色用批量 `delete()` 触发 `SAWarning: expected to delete N row(s); 0 were matched` 并连带报错 → 改用关系级 `role.permissions.clear()` / `user.roles.clear()`；

## 11.1 本轮代码优化（都在鉴权/授权范围内）

| #   | 改了什么                                                                           | 为什么                                               |
| --- | ------------------------------------------------------------------------------ | ------------------------------------------------- |
| 1   | 登录失败计数从「只按输入字符串」改成「输入标识 + 解析到的 user_id」双维度，成功时用户名 / 邮箱 / user_id 三处一起清         | 原来同一账号用用户名、邮箱各试 5 次就能绕过锁定；现在共享同一额度，且任一通道登录成功都会清干净 |

## 13. 边界说明（没做的部分，明确告诉你）

1. `app/modules/user/service.py` 以你补发的那份为基础合并：`get_by_id`、`get_by_username_or_email`、`username_taken`、`email_taken`、`register`、`authenticate` 原样保留并被新流程复用；`authenticate` 的 `username` 参数对齐为 `identity` 并追加 `request` 用于审计；`update_profile` 保留「只更新传入字段」的语义，写入目标改为 `user_account` 的列。新增的邮箱验证码、改密、登出、失败计数都在同一文件内。
2. `school_info` / `study_plan` / `exam_*` 等业务表本次不建；个人中心的「目标院校」暂时只能填地区（`target_area`），编号列 `target_school_id` 已按 ER 图保留，择校模块上线后接入。
3. 邮箱唯一索引意味着**一个邮箱只能绑一个账号**；如果你要允许多账号共用一个邮箱，得去掉 `email` 的 unique，并改成「邮箱 + 验证码命中多条时让用户选账号」——那会牺牲登录体验，建议保持现状。
4. 审计日志只记录鉴权/授权相关动作与登录/改密，不记录业务读写（否则数据量会失控），且只增不删，需要自己加归档策略。
5. 令牌仍是 JWT（无状态）+ blocklist 混合模式：吊销依赖 Redis/内存 KV，Redis 全挂时降级进程内存储，多 worker 会有一致性窗口，见 6.1。
