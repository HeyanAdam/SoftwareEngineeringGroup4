同一批用户，两个系统，同台对照

系统A（无Redis）：没有内存数据库，每个请求一个真实 MySQL InnoDB 事务直打磁盘库 —— BEGIN → SELECT 快照读（不加锁）→ 应用层判断 → UPDATE（行锁）→ COMMIT。 同一行商品的 UPDATE 被行锁串行化，写事务毫秒级（含 fsync，比 Redis 慢百倍以上）。

系统B（配Redis）：库存预扣是真实 EVAL seckill.lua 原子脚本（查·判·扣一口气，亚毫秒）， 抢到的订单 LPUSH 进真实 Redis 队列，由后台消费者 BRPOP 异步落库 MySQL，用户先拿到响应。

点击开始后，系统先真实并发执行全部请求，再按每条请求的真实耗时逐条回放：到达 → 排队等待 → 处理 → 成功/售罄/超时。 演示时可打开 redis-cli / mysql 客户端同步验证数据（GET stock:DUEL-B / SELECT stock FROM goods WHERE id='DUEL-A'）。

Redis 为什么快 · 为什么不会超卖

核心答案就两个字：单线程。Redis 用一个线程把每条命令排队一条条执行 —— 没有锁竞争、没有上下文切换，每条命令执行时间亚微秒级。 下面这个面板把「并发到达 → 队列排队 → 逐条执行」的真实过程画出来， 并对比分开两条命令（有竞态窗口）vs Lua 一条原子脚本（无竞态）的天壤之别。

控制面板

不安全模式：先发 GET 查库存，再发 DECR 扣减 —— 两条命令之间有竞态窗口，必超卖。
Lua 原子：判重+查库存+扣减+记账 四步在一条脚本内完成，零超卖。

热点数据：6 个商品，谁在 MySQL、谁在 Redis

所有商品的真身都存在 MySQL里。Redis 只存一份副本，给被反复访问的商品用。 下面 6 个商品里，⚪ 只在 MySQL 的商品第一次被打开时要去数据库查（慢）， 查完就写进 Redis；🟢 已在 Redis 的商品直接读内存（快）。 某个商品累计被打开 3 次就会被打上 🔥 热点 标记，缓存时间从 60 秒延长到 300 秒 —— 这就是「商品变成热点后自动放进 Redis」。注意：缓存都有 TTL，到期就会被 Redis 自动删除， 热点商品只是活得更久（300 秒），并不是永久驻留。

⚪ 只在 MySQL 🟢 已在 Redis 🔥 热点商品（TTL 300s） 点卡片就能打开它的详情页
